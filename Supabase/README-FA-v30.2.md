# راه‌اندازی زیرساخت ابری WoundAI v30.2

این بسته، لایه اتصال Supabase Auth و PostgREST، کنترل عضویت مرکز، سیاست‌های RLS، جداول مراجعه/نوبت و audit سمت پایگاه داده را اضافه می‌کند. **اتصال ابری هنوز جایگزین ذخیره‌سازی محلی فرم‌های فعلی نشده و مهاجرت خودکار داده انجام نمی‌دهد.**

## پیش‌نیازهای غیرقابل‌چشم‌پوشی

1. یک پروژه اختصاصی Supabase در منطقه جغرافیایی و حوزه حقوقی مورد تأیید سازمان بسازید.
2. پیش از ورود هرگونه اطلاعات بیمار، قرارداد پردازش داده، محل میزبانی، GDPR/DPIA یا قوانین محلی و الزامات نرم‌افزار پزشکی را بررسی کنید.
3. در Authentication تنظیمات ثبت‌نام/دعوت، بازیابی حساب، سیاست گذرواژه، ایمیل و MFA را مطابق سیاست سازمان فعال کنید.
4. فعال‌سازی TOTP در رابط WoundAI موجود است؛ سیاست‌های نوشتن RLS در این migration به نشست MFA با `aal2` نیاز دارند.
5. هرگز `service_role`, `sb_secret_*`, رمز دیتابیس یا کلید امضای JWT را در مرورگر یا فایل استاتیک قرار ندهید. فقط URL پروژه و Publishable/Anon key مجاز است.

## ترتیب Migration

در SQL Editor پروژه آزمایشی، ابتدا migration پایه موجود در `supabase/migrations/202611100001_woundai_core.sql` و سپس `supabase/migrations/202611140002_woundai_v30_2_backend.sql` را اجرا کنید. پس از هر مرحله خطاهای SQL Editor را بررسی و خروجی را ذخیره کنید.

Migration دوم:
- نشست MFA سطح AAL2 را برای عملیات نوشتن با نقش owner/admin/clinician لازم می‌کند.
- RPC امن ایجاد مرکز و تعیین مالک اولیه را اضافه می‌کند.
- RPC افزودن عضو را با محدودیت نقش و MFA اضافه می‌کند. حساب کاربر مقصد باید قبلاً در Auth ایجاد/دعوت شده باشد.
- جداول `encounters` و `appointments` را با کلیدهای مرکب tenant/patient/wound اضافه می‌کند.
- RLS خواندن را به اعضای همان مرکز و نوشتن را به نقش‌های مجاز محدود می‌کند.
- audit تغییرات رکوردهای بالینی و عضویت را در پایگاه داده ثبت می‌کند؛ فقط نام فیلدهای تغییرکرده ذخیره می‌شود، نه مقادیر بالینی.
- Storage را خصوصی نگه می‌دارد و نام پوشه نامعتبر را بدون خطای cast رد می‌کند.

## پیکربندی رابط

در صفحه «امنیت، حریم خصوصی و دسترسی»:
1. Project URL و Publishable/Anon key را وارد و ذخیره کنید.
2. حسابی که از قبل در Supabase Auth ایجاد یا دعوت شده را وارد کنید.
3. عامل TOTP را با برنامه Authenticator ثبت و کد را تأیید کنید. وضعیت نشست باید `aal2` باشد.
4. مرکز موجود را بارگذاری یا یک مرکز آزمایشی ایجاد کنید.
5. «آزمایش خواندن پرونده‌های ابری» فقط فهرست خلاصه پرونده‌های ابری را می‌خواند.

کلید عمومی پروژه در LocalStorage نگهداری می‌شود؛ این کلید محرمانه نیست. توکن نشست فقط در `sessionStorage` همان تب/نشست نگهداری می‌شود و با خروج پاک می‌شود. از دستگاه مشترک استفاده نکنید.

## مدل داده و محدوده فعلی

- جداول پایه: clinics, clinic_members, patients, wounds, wound_images, assessments, care_plans, audit_events.
- جداول v30.2: encounters, appointments.
- فایل‌ها در bucket خصوصی `wound-images` قرار می‌گیرند و مسیر پیشنهادی آن `<clinic_uuid>/<patient_uuid>/<wound_uuid>/<filename>` است.
- رابط فعلی ثبت بیمار/زخم/ارزیابی همچنان از LocalStorage استفاده می‌کند. فهرست ابری فقط قابلیت اتصال و خواندن را آزمایش می‌کند؛ هیچ داده محلی به سرور منتقل نمی‌شود و هیچ نوشتن پرونده‌ای از فرم اصلی انجام نمی‌شود.
- گزارش audit در این مرحله تغییرات ایجاد/ویرایش/حذف و عضویت را ثبت می‌کند. رویدادهای مشاهده/خواندن هنوز به audit سروری متصل نشده‌اند.
- رمزنگاری at-rest پایگاه داده و Storage به تنظیمات و تضمین‌های سرویس میزبانی وابسته است؛ این migration رمزنگاری سمت برنامه یا مدیریت کلید مستقل ایجاد نمی‌کند.
- پشتیبان‌گیری خودکار، PITR و آزمون بازیابی باید در تنظیمات پروژه/پلن Supabase فعال و جداگانه آزموده شوند.

## آزمون پذیرش پس از استقرار

با دو حساب آزمایشی و دو مرکز آزمایشی، این موارد را بررسی کنید:

1. کاربر بدون عضویت، هیچ رکوردی از مرکز را نخواند.
2. عضو مرکز A نتواند پرونده مرکز B را بخواند.
3. نقش viewer/reviewer نتواند بیمار، زخم، ارزیابی، نوبت یا مراجعه ایجاد/ویرایش کند.
4. نقش clinician با نشست AAL1 نتواند عملیات نوشتن انجام دهد؛ پس از MFA و AAL2 مجاز شود.
5. admin نتواند نقش owner اعطا کند؛ فقط owner قادر باشد.
6. درخواست دست‌کاری مستقیم `audit_events` از کلاینت رد شود.
7. تغییر بیمار/زخم/ارزیابی/نوبت/مراجعه، audit event ایجاد کند و مقادیر حساس را در metadata نگذارد.
8. فایل Storage از مرکز دیگر قابل خواندن یا نوشتن نباشد؛ bucket عمومی نباشد.
9. حذف بیمار، رفتار cascade و audit را مطابق سیاست نگهداری مصوب بررسی کنید. برای محیط عملیاتی، حذف فیزیکی ممکن است نیازمند فرایند retention/soft-delete باشد.
10. پشتیبان و بازیابی پایگاه داده را در پروژه staging اجرا کنید.

## محدودیت و وضعیت تأیید

تست‌های محلی این بسته، اعتبارسنجی کلاینت و بررسی ایستا را پوشش می‌دهند. Migration روی پروژه Supabase واقعی اجرا نشده؛ RLS، MFA، Storage و جداسازی دو tenant تا زمان اجرای آزمون‌های بالا **تأییدشده محسوب نمی‌شوند**. این بسته برای ورود اطلاعات هویتی یا درمانی واقعی مجاز نیست تا بازبینی امنیتی، حقوقی و بالینی تکمیل شود.
